# Threat model: data layer (P2-1, P2-2, P2-5, P2-6)

The webhook inbox (`app.webhook_deliveries`, P3-2) has its own threat table (W1–W13) in
[ADR 0007](../../docs/adr/0007-webhook-inbox.md); its database rows are W4, W5, W11–W13. The
installation lifecycle (P3-3: worker role, org creation, inbox claim path, erasure sweep) has its
own table (L1–L20) in [ADR 0009](../../docs/adr/0009-installation-lifecycle.md).

Companion to [ADR 0003 tenancy](../../docs/adr/0003-tenancy.md) and
[ADR 0005 migrations and roles](../../docs/adr/0005-migrations-and-roles.md). Each row names the
test that proves the control; the tests live next to the code in `src/*.test.ts` and run in CI
against a real Postgres (Testcontainers, same pgvector image digest as `docker-compose.dev.yml`).
Rows marked "(review)" were added after the independent security review of the first version.

## Assets

- Tenant data: PR metadata, analyses, review drafts, memory, embeddings, usage (`public.*`).
- Encrypted secrets: wrapped org data keys, user forge tokens, BYOK keys (`*_ciphertext`).
- The audit trail (`audit_events`): evidence that must survive a compromised application.
- Database credentials: `rocky_app` (application), the migrator/owner, `rocky_retention`.

## Attackers

- Another tenant driving the application through normal requests, or through a bug that
  forgets `WHERE org_id = …`, concatenates SQL, or passes an attacker-controlled org id.
- Malicious PR content (titles, file paths, comments) that ends up in SQL parameters or
  `jsonb` columns and later in prompts (handled in P4; here it is only data).
- An attacker holding the application's database credentials (server or worker compromise).
- An operator mistake: running ad-hoc SQL with the wrong role, or a migration that forgets
  RLS on a new table.

## Residual risks (accepted, documented)

- The migrator/owner role can disable triggers and policies; it is a deployment credential,
  never given to the application (ADR 0005). Operators must treat it like a root credential.
- Code running inside `withOrg(A)` holds a transaction. The statement guard (T7) is a denylist on
  statement text and the second layer; a determined insider with code-execution could still issue
  the raw protocol through another client library. What holds then is the first layer: the
  application role cannot run procedural code or reach `set_config` indirectly, every tenant
  table has RLS, and the roles are split. `SET app.org_id` itself cannot be taken away from the
  role (custom placeholders are user-settable), so an attacker who sends raw statements can
  still switch tenant inside one transaction; the commit-time recheck catches a switch that is
  not switched back. Provisioning (ADR 0005 §2) is superuser-only and verified by migration 0001.
- `rocky_app` can `pg_terminate_backend` other sessions of its own login role (Postgres allows
  that for the same role). That is availability, not isolation, and only within the application.
- `audit_events.id` and `llm_usage.id` are global identity sequences, so a tenant can infer the
  overall write volume of the deployment from gaps in its own ids (review #13). Accepted: the
  ids carry no tenant information and are never exposed as pagination cursors across tenants.
- The audit floor equals the configured audit period (30 days minimum). A compromised app can
  still run the purge early, but it only removes rows already past the period the operator
  chose; shortening the period needs the migrator credential (review #5).
- `retention.delete_org` is callable (since P3-3, by the worker role only, ADR 0009) for any org whose grace period has elapsed. The
  grace period is enforced by a trigger the app cannot bypass, so the window between "scheduled"
  and "deleted" is always at least `org_deletion_grace` days, long enough for the uninstall to be
  noticed and cancelled (set `delete_after` back to NULL). The deletion itself cannot be audited
  per tenant (the tenant is gone); since P3-3 it writes a tombstone to `app.org_deletions` and the worker logs it. `rocky_retention` holds `UPDATE` on `orgs`
  only because `SELECT … FOR UPDATE` requires it (and an UPDATE policy); none of its functions
  issues an UPDATE.
- The audit `created_at` stamp applies to every role. Tests that need old rows disable the
  trigger as the superuser inside one transaction (`plantAuditEvent`); product code never does.
- `orgs (forge, installation_id)` is globally unique, so a tenant could learn whether an
  installation id exists by attempting an insert. Installation ids are not secret.
- Application logs are not in the database; "logs" retention here means finished `jobs` rows.
  Pino log retention is a hosting concern (P2-4, infra).
