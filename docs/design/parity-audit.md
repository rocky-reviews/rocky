# POC parity audit (P6-9)

A fresh comparison of the real app (fixture pr-847) with `design-poc/index.html`, state by state,
at 375/1024/1440 px × light/dark. It checks the ticked items in [`poc-parity.md`](poc-parity.md)
against what is actually on screen. Every difference is listed below with a severity and its
resolution: **fixed** (with the change and the test that holds it) or **accepted** (with the
reason).

The audit ran first (commit "P6-9: parity audit report"); the fixes followed on top of P6-8
(accessibility & performance), which changed some of the same visuals. The side-by-sides below
are the **re-capture after the fixes**; the "before" pictures are in the audit commit's
`docs/design/parity-audit/`.

**Result:** 32 differences found: 0 blockers, 3 should, 29 nits. 11 fixed (all 3 should and 8
nits), 21 accepted (D9 turned out not to be a difference and moved to Accepted). None open.

## Method

- Both sides were driven into the same state by a throwaway Playwright spec, in the same browser:
  the app on the e2e review API mock (`apps/web/e2e/test.ts`), the POC from `file://` with its
  own state (`S`) set through `page.evaluate`. Both were scrolled to the same anchor (the F1 draft
  card, the composer, the end of the file, the end of the panel, the bottom of the modal) so the
  pictures line up. Toasts were hidden except in the toast states, and animations were off.
- 25 states × 3 widths × 2 modes = 146 pairs (a state the POC has no layout for at a width, such
  as the right panel below 1180 px, shows a "Not in the POC" placeholder next to the app's
  drawer). The full set is a working copy in `artifacts/screenshots/P6-9/{poc,app,compare}/`,
  which is gitignored (50 MB). The 34 side-by-sides that the findings link to are committed
  under [`parity-audit/`](parity-audit/), reduced to 256 colours (about 7 MB). The capture spec
  is kept next to the working copy (`artifacts/screenshots/P6-9/capture.spec.ts.txt`) and not
  committed (see "Follow-ups").
- Top-bar heights and horizontal overflow were measured in the DOM at each width.
- App-only states (analysis states, drawers, inbox, Finish review errors) were checked for
  consistency against the POC's style from the existing baselines in
  `apps/web/e2e/__screenshots__/`, because the POC has no reference for them.

## Follow-ups

- The visual baselines were regenerated with `--update-snapshots=all`: with
  `maxDiffPixelRatio: 0.002` (about 2,600 px at 1440 × 900) a one-line text change passes, so
  `--update-snapshots` alone had left about 70 baselines showing the old text (UI-verifier).
  A tighter ratio, or a text assertion next to each screenshot, would catch such a change.

- The capture spec is not committed: as an `e2e/*.visual.spec.ts` it would run in every CI pass
  (about 1.5 min, 50 MB of output). If a repeatable audit is wanted, it could live behind its own
  Playwright project that CI skips.
- On a short phone the list box can be as small as 64 px (whole, but scrolled), and long
  warnings (many unviewed files, an in-flight attempt) can still push the verdict below the fold;
  the modal then scrolls with its head and footer pinned (ADR 0031 residual risks).
