# POC parity audit (P6-9)

A fresh comparison of the real app (fixture pr-847) with `design-poc/index.html`, state by state,
at 375/1024/1440 px × light/dark. It checks the ticked items in [`poc-parity.md`](poc-parity.md)
against what is actually on screen. Every difference is listed below with a severity and a
proposed resolution: **fix** (with the file it lives in) or **accept** (with the reason).

This round is the audit only. The fixes are made after P6-8 (accessibility & performance) merges,
because P6-8 also changes some of the same visuals (badge hit areas and contrast).

## Method

- Both sides were driven into the same state by a throwaway Playwright spec, in the same browser:
  the app on the e2e review API mock (`apps/web/e2e/test.ts`), the POC from `file://` with its
  own state (`S`) set through `page.evaluate`. Both were scrolled to the same anchor (the F1 draft
  card, the composer, the end of the file, the end of the panel, the bottom of the modal) so the
  pictures line up. Toasts were hidden except in the toast states, and animations were off.
- 25 states × 3 widths × 2 modes = 146 pairs (a state the POC has no layout for at a width, such
  as the right panel below 1180 px, shows a "Not in the POC" placeholder next to the app's
  drawer). The full set is a working copy in `artifacts/screenshots/P6-9/{poc,app,compare}/`,
  which is gitignored (50 MB). The 34 side-by-sides that the findings link to are committed
  under [`parity-audit/`](parity-audit/), reduced to 256 colours (5.8 MB). The capture spec is
  kept next to the working copy (`artifacts/screenshots/P6-9/capture.spec.ts.txt`) and not
  committed (see "Follow-ups").
- Top-bar heights and horizontal overflow were measured in the DOM at each width.
- App-only states (analysis states, drawers, inbox, Finish review errors) were checked for
  consistency against the POC's style from the existing baselines in
  `apps/web/e2e/__screenshots__/`, because the POC has no reference for them.

## Checklist cross-check

Ticked items in `poc-parity.md` that do not match the app:

- **Intentional differences, "Top bar at ≤ 760 px"**: "The bar is about 96 px tall" — it is 116 px
  and the title is cut to ten characters (D1).
- **Top bar, "Finish review" primary button with pending-comment count** (ticked with
  `finish-375-dark`): below 760 px the label is hidden on a premise the POC does not support (D2).
- **AI drafts, "Accept (a) → becomes '@you · Pending · from AI draft'"**: the app says "You"
  (D10).
- **Finish review, "Request changes pre-selected (with reason)"**: true, but the pick is out of
  view when the modal opens (D3).

Every other ticked item was found on screen as described. The unticked items (change map Retry,
Ask, `/` opens Ask, the "Polished" toast) are still missing, as their notes say.

## Needs a decision

1. **Finish modal height (D3).** Cap the list with its own scroll, or collapse each comment's
   Markdown to a few lines with "Show all"? Either keeps ADR 0031's "what GitHub receives is what
   the person reads"; the collapse hides part of it until expanded.
2. **Phone top bar (D1, D2).** Which control gives up its place so the title and a labelled
   Finish button fit: the theme toggle (also on `m`), or the "?" button that P6-5 deliberately kept
   below 760 px?
3. **"You" or "@login" (D10).** The POC used the login. "You" is friendlier; "@login" matches what
   GitHub will show and what the modal and toast already say.

## Not compared

- **Ask (P9-2)**: not built; the POC reference is [25](parity-audit/25-ask-1440-light.png).
- **App-only states** (no analysis, analysing, awaiting approval, failed, superseded,

  They follow the POC's cards, pills, notices and modal; the only finding is D12.
